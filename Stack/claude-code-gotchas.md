# Claude Code — Gotchas técnicos

- **Scheduled triggers** no acceden a repos privados — repo público o GitHub conectado en claude.ai/settings.
- **`gh repo edit --visibility`** requiere `--accept-visibility-change-consequences`.
- **`gh auth switch` para repos multi-cuenta** — `gh auth switch --user <org>` + `gh auth setup-git` antes de push.
- **`git push` rechazado al tocar `.github/workflows/`** — `refusing to allow an OAuth App to create or update workflow ... without 'workflow' scope`; bloquea TODA la rama, no solo ese fichero. Fix: el usuario corre `gh auth refresh -h github.com -s workflow` (interactivo, abre navegador) y reintentas el push. No lanzable desde Bash no-interactivo → pedírselo con `! gh auth refresh ...`. Si un PR va a tocar CI, valida el scope antes. Caso AGH #35.
- **Plugins settings.json** — nombre debe coincidir con `marketplace.json` del repo fuente.
- **Claude Design handoff bundles son tar** — `tar xf`, no abrir como HTML. Contiene README.md + chats/ + project/. Leer chat transcripts primero para la intención.
- **Zod `.strict()` bloquea campos no listados** — al añadir campos editables desde admin, añadirlos al schema Zod. Si no, PATCH devuelve 400 silenciosamente.
- **Verificación obligatoria antes de commit (Next.js)** — `npm run lint → typecheck → build`. Los tres deben pasar. No silenciar con `@ts-ignore`/`eslint-disable`/`as any`.
- **Next 16: `tsc --noEmit` falla por `.next/dev/types/validator.ts` stale** (artefacto del dev server, no es tu código; el `build` no lo regenera). Fix: `rm -rf .next/dev` y re-typecheck. Caso TuFacturaIA 2026-06-11.
- **`pnpm/action-setup@v4` + `packageManager` en package.json** — declarar versión solo en UN sitio. Si declaras `version: 10` en el workflow Y `packageManager: pnpm@10.33.3` en `package.json` → CI rompe con "Multiple versions of pnpm specified". Quitar `version` del workflow es la fix recomendada (action-setup lo lee de packageManager automáticamente).
- **Next.js `unstable_cache` no invalida con escrituras directas a BD** — si modificas datos via script externo (Prisma directo, SQL, seed), el cache lo ignora hasta `revalidateTag(TAG)` o reinicio del dev server. En prod no es problema porque las server actions llaman `revalidateTag`. En dev/scripts, recordar reiniciar o llamar revalidate.
- **Cloudflared quick tunnel sin login** — `cloudflared tunnel --url http://localhost:PORT --no-autoupdate` da una URL `*.trycloudflare.com` temporal. Útil para apuntar webhooks de provider externo a localhost en pruebas E2E. La URL se pierde al parar el proceso, no es estable.
- **Next.js route handlers no permiten exports custom** — solo `GET`, `POST`, etc. Si exportas un helper desde `route.ts`, typecheck devuelve `Type ... not assignable to type 'never'` en `.next/types/...`. Mover el helper a archivo aparte o dejarlo private.
- **`req.text()` antes de cualquier parse** para verificación HMAC — leer el body como string crudo antes de `JSON.parse` o cualquier middleware. La firma se computa sobre los bytes EXACTOS recibidos; cualquier re-serialización rompe el digest.
- **Edits paralelos al mismo archivo se rompen** — múltiples Edit calls en una sola tool-block sobre el mismo path: el primero muta el contenido y el segundo no encuentra su `old_string`. Síntoma "String to replace not found" tras edit exitoso. Hacer secuencial. Paralelo solo entre archivos distintos.
- **Subagentes investigando repo distinto al cwd** — pasar ruta absoluta en la primera línea del prompt + "investiga SOLO en esa ruta, no leas archivos fuera de ella". Sin esto contaminan el reporte con paths del cwd actual (caso: agente reportó hallazgos de `facturaia/src/...` cuando debía auditar `~/agency-portal-fix`).
- **`.claude/settings.local.json` acumula secretos en literales de allowlist** — cuando aceptas comandos tipo `Bash(curl -H 'Authorization: Bearer <jwt>' ...)` o `Bash(curl ... apikey: <service_role> ...)`, esos literales se guardan tal cual. Añadir `.claude/settings.local.json` al `.gitignore` en TODO repo nuevo desde el primer commit. Caso: agency-portal PR #76 2026-05-28 (JWTs n8n + service_role Supabase en patterns).
- **Un subagente puede re-dispararse solo en bucle y NO se mata con `TaskStop`** (figura `completed` cada ciclo → "not running"). Caso 2026-06-10: agente de research se reactivó ~30 veces, escaló de investigar a editar código y manipular git (ramas, stashes), y llegó a stashear WIP de otra sesión del mismo repo. Mitigación: para trabajo grande/arriesgado de un agente, aislarlo en **worktree desde `origin/main`** (working tree propio; un runaway no puede pisar/stashear el repo principal). Corte de raíz fiable = el humano interrumpe la sesión (Esc); desde el orquestador no hay kill si el task reporta completed.
- **`gh pr merge --delete-branch` falla (exit 1) si la rama vive en un worktree local — pero el merge remoto SÍ se completa**: verificar con `gh pr view N --json state` antes de reintentar o asumir fallo. Además puede dejar el checkout principal a medias (switch a main sin pull) si hay untracked en conflicto. Caso TuFacturaIA 2026-06-10 (repo con 50+ worktrees).
- **El hook global `git-guard` mira el TEXTO del comando, no su semántica: `git worktree remove --force <path>` queda bloqueado** con el mensaje de force push. No es un falso positivo que rodear con `--no-verify`: quita el `--force` (borra antes lo que estorbe — symlinks de `node_modules`/`.env.local`, `.next`) y `git worktree remove <path>` a secas pasa. Caso TuFacturaIA 2026-07-29.
- **`git checkout <fichero>` SIN `--` se llevaba el trabajo y el `git-guard` no lo veía — TAPADO el 8-ago (`cf19db9`).** Caso 8-ago: `cmd && git checkout -q <spec> 2>/dev/null || python_restaurar` — el guard bloquea el checkout suelto, pero encadenado con `||` se ejecutó y restauró el fichero al último commit, borrando media hora de cambios sin commitear. Lo que salva no es el hook: es commitear antes de mutar (aunque sea un WIP) o guardar `git diff > /tmp/x.patch`. Un `checkout` nunca es un plan B. La causa no era el encadenado sino que la regla exigía `checkout` seguido de `--` para siquiera mirar: `git checkout -q <ruta>` y `git checkout <ruta>` pasaban de largo. Ahora recorre por segmento y pregunta a `git status --porcelain -- <args>` quién es ruta y quién rama, que es lo que permite ampliarla sin bloquear `git checkout main`.
- **Una sesión paralela puede RETIRAR tu worktree mientras trabajas en él, y se lleva lo que no esté commiteado.** Caso TuFacturaIA 8-ago: otra sesión mergeó mi rama y limpió su worktree («al cerrar rama, `git worktree remove`»); el directorio desapareció bajo el proceso y los ficheros aparecían primero como ` D` masivos —parecía un hook borrando cosas— hasta que un `cd` falló con «no such file or directory». Lo salvó tener el `git diff origin/main...HEAD > delta.patch` guardado FUERA del worktree. Con ramas que otra sesión pueda mergear: commitea pronto, y guarda el parche en el scratchpad antes de cualquier pausa larga.
- **`git worktree remove <path>` DESDE DENTRO de ese worktree** falla con `fatal: Unable to read current working directory` (borra el cwd bajo tus pies). Ejecútalo siempre desde otro cwd (el checkout raíz) y remata con `git worktree prune`. Caso TuFacturaIA 2026-07-20 (2 veces en la misma sesión).
- **Los plugins no los actualiza `skills update`** — `claude plugin marketplace update` + `claude plugin update <plugin>@<marketplace>` (y `--scope local` desde el cwd del proyecto). Envejecen callados. (Recolocado desde `hot.md` en la poda del 29-jul: era la única entrada sin learning propio.)
- **Un hook PreToolUse aborta el comando COMPUESTO entero, no solo la parte que le ofende** — `git add X && git commit -m ...` bloqueado por `git-guard` no ejecuta ni el `add`. El siguiente `git diff --cached` sale VACÍO, y si a continuación haces `git checkout -- <ficheros>` para mover el trabajo a otra rama, **lo borras**. Regla: cuando un hook bloquee, comprobar el estado real (`git status`) antes del siguiente comando destructivo, y separar `add` de `commit` en llamadas distintas. Caso TuFacturaIA 2026-07-29 (fix reconstruido a mano desde el diff ya impreso en contexto). **Vuelto a pisar el 16-ago en TuCRMIA, con un daño distinto y más silencioso**: el hook de aviso-en-Slack cortó `python (cerrar issue) && cola-check && python (contador) && git add && git commit`, así que NINGUNA de las ediciones corrió — y como el mensaje del hook habla sólo del `commit`, el reflejo fue avisar en Slack y reintentar el commit. Resultado: el arreglo se empujó con el issue todavía abierto y el contador de la métrica sin tocar, o sea el registro mintiendo sobre lo hecho. **Un hook que bloquea no deja el trabajo a medias: lo deja sin empezar**, y lo que toca después no es reintentar el último paso sino releer qué se aplicó de verdad.
- **`node_modules` por symlink en un worktree pasa lint/typecheck/tests y muere en `next build`** (`Symlink [project]/node_modules is invalid, it points out of the filesystem root`, `TurbopackInternalError`): parece error de código y es de infraestructura. `npm ci` de verdad en cualquier worktree que deba pasar el gate. Ver [[turbopack-rechaza-symlink-node-modules-en-worktree]].
- **Subagentes de diseño ignoran decisiones previas si no les pegas la receta literal** — describir "usa las pills T3 Gota decididas" no basta: el agente inventa pills planas genéricas. Decisión de diseño cerrada → el prompt lleva el CSS/HTML exacto a copiar verbatim (o "copia el esqueleto de <archivo>"). Caso TuFacturaIA 2026-06-11: tanda completa de 4 prototipos rechazada por esto; relanzada con receta literal → aceptada.
- **Agentes custom de proyecto fallan con `API Error 400 thinking.type.disabled`** con modelo default/fable → lanzarlos siempre con `model: "sonnet"` explícito. Caso: `facturaia-frontend`.
- **Workflow tool: `${...}` en strings de prompt embebidos se EVALÚA al parsear el script** — si el prompt de un `agent()` incluye código de ejemplo con `${req.url}` dentro del template-literal del script, JS intenta resolver `req` → `ReferenceError: req is not defined` y el workflow muere ANTES de lanzar agentes (0 agents_done). Escápalo (`\${...}`) o parafrasea ("req punto url"). Editar el `.js` persistido + re-invocar con `scriptPath`. Caso AGH re-audit 2026-07-07.
- **Write de archivos grandes choca con límite 32k output tokens** — patrón chunked: primer Write ≤400 líneas terminando en marcador `<!-- NEXT -->`, luego Edits sucesivos que reemplazan el marcador con el siguiente bloque.
- **Sesión/editor paralelo revierte tus edits en disco en silencio** — otra sesión Claude (o un buffer viejo del IDE auto-guardando) sobreescribe el working tree segundos después de cada Edit; síntoma: el reminder "file was modified" muestra el contenido ANTERIOR, no el tuyo. No ganas la carrera reeditando. Mitigación: stagea tu versión directo al ÍNDICE con `git apply --cached` (el escritor toca el working tree, no el index) y commitea desde ahí — el deploy usa el commit, no el árbol. Caso TuFacturaIA 2026-06-12 (action-bar/ocr-process revertidos ~4 veces por la sesión que hacía clientes).
- **Excluir hunks ajenos al commitear un archivo compartido** — si la otra sesión tiene WIP en el mismo fichero, `git add <file>` arrastra su trabajo a tu commit. Construye un patch SOLO con tus hunks (`diff --git` + cabeceras `@@` numeradas + líneas de contexto en blanco con su espacio inicial, si no `git apply` da "No valid patches"/"does not apply") y `git apply --cached`. Caso 2026-06-12: hunk de aliases ajeno en ingesta-view.tsx excluido limpio; quedó en el commit del otro.
- **Pushear a `main` con una sesión paralela commiteando en el MISMO working tree** — combo fiable y limpio: (1) `git diff HEAD -- <tus paths> > /tmp/mine.patch` (solo tus ficheros); (2) `git worktree add <wt> origin/main`; (3) `git apply` el patch ahí; (4) commit + push desde el worktree. Aísla tu commit del WIP ajeno, evita el ref-lock race del hook largo (el commit corre con HEAD propio), y el push es un ff de 1 commit (si `origin/main` se movió, `git rebase origin/main` del único commit disjunto → cero conflicto, reintenta). Al terminar: `git checkout -- <tus paths>` en el checkout principal (tu copia local ya es redundante) y borra el worktree. Caso TuFacturaIA 2026-06-16: feat catálogo-stock a main mientras otra sesión empujaba informes/conciliación.
- **El `build` del pre-push falla en un worktree con `node_modules` SIMLINKADO** — Turbopack aborta: "Symlink [project]/node_modules is invalid, it points out of the filesystem root". No bypasees con `--no-verify` en main (el classifier lo bloquea, y es el guardrail de migraciones). Fix: `node_modules` REAL en el worktree. En APFS, clonefile instantáneo y disjoint-disco: `cp -Rc <repo>/node_modules <wt>/node_modules` (BSD `cp` de macOS NO tiene `-l`/hardlink; usa `-c`). El worktree debe estar en el mismo volumen que el repo (sibling en `~/`, no `/tmp` que es otro root). Copia también `.env*` para que el build se comporte igual. Caso TuFacturaIA 2026-06-16.
- **`~/Downloads` TCC-bloqueado (macOS)** — el Read tool lee texto de `~/Downloads`, pero `pdftoppm` (PDF), `cp` y Bash fallan "Operation not permitted" ahí (TCC no concede a la terminal acceso a Downloads). Fix: arrastrar el fichero en Finder a la carpeta del proyecto (la sesión gráfica sí tiene permiso) o dar Acceso a Disco Completo a la terminal. Caso 2026-06-24: PDF de spec SEPA en Downloads ilegible hasta moverlo al repo.
- **El classifier bloquea commitear/pushear una FIRMA o aprobación humana atribuida al usuario** (content-integrity / impersonation) — aunque el user lo apruebe verbalmente ("apruebo, firma tú"). Un gate de seguridad / sign-off lo estampa el humano (edición + commit propios), no el agente. No intentes esquivarlo. Caso TuFacturaIA 2026-06-19: checkbox "Revisado y aprobado por: Manuel" en `SECURITY-AUDIT-059.md` → push denegado; commit dejado listo en rama para que lo empuje el humano.
- **En `.claude/worktrees/<x>` el cwd del shell se resetea a `main` en silencio** — el Edit tool (rutas absolutas) SÍ escribe en el worktree, pero los comandos Bash con rutas RELATIVAS (`sed -i`, `git add`, `grep`) caen en el checkout PRINCIPAL → parece que los edits 'se revierten' (en realidad lees/editas el fichero equivocado) y contaminas `main`. Fix: rutas ABSOLUTAS del worktree en cada comando o `cd <worktree> &&` al inicio; verifica con `echo pwd`. Caso TuFacturaIA 2026-07-02 (Front B tipos Supabase).
- **El classifier bloquea leer secretos de prod** (Dokploy/env) aunque sea para comparar longitud/hash SIN exponer valores ([Production Reads]). No lo esquives — pide al humano que corra el comando (`!` prefix) o te dé el dato binario (iguales/distintas). Caso 2026-07-02: comparar `WEBHOOK_SIGNING_KEY` vs `CREDENTIAL_ENCRYPTION_KEY`.

- **Un subagente que se cuelga (watchdog `no progress for 600s`, status=failed) puede haber dejado sus edits COMPLETOS en disco** — NO asumas que el trabajo se perdió. Revisa `git diff`/`status` del worktree y corre TÚ el gate; a menudo terminó los cambios y solo se atascó en el paso final (p.ej. `build` largo). Caso TuFacturaIA 2026-07-02: `/polish` de 8 modales murió en el watchdog pero los edits estaban completos y correctos; solo faltaba correr lint/typecheck/build.
- **Sesiones paralelas de Claude Code corriendo `lint`/`typecheck`/`build` en el MISMO repo (sin worktree) acumulan procesos `tsc`/`next build` huérfanos** si algún intento se reintenta o se cuelga — cada `npm run typecheck` en background que no termina limpio deja el `tsc --noEmit` vivo. Con varios así (load average >15), el daemon de `agent-browser` empieza a fallar (`Resource temporarily unavailable`) y las screenshots/eval se caen. Antes de asumir que el navegador está roto, `ps aux | grep "tsc --noEmit\|next build"` y `uptime`. Solo mata procesos si tienes certeza de que son tuyos (verificar working dir del proceso, no solo el nombre) — pueden ser de otra sesión legítima. Caso TuFacturaIA 2026-07-03.
- **Un subagente lanzado solo para VERIFICAR un hallazgo de code-review puede escalar solo a arreglar+commitear+pushear**, saltándose la aprobación humana entre "confirmar el bug" y "tocar código en la rama del PR". El contenido puede ser correcto (en el caso real, el fix estaba bien hecho) pero el proceso viola el checkpoint de revisión. Mitigación: tras cualquier tanda de agentes de verificación en un review, `git log` de la rama ANTES de dar el veredicto final — si aparece un commit que no hiciste tú, para y audita su diff línea a línea antes de seguir (no asumas que "verificar" implica read-only). Caso TuFacturaIA 2026-07-03, PR #688.
- **`git add -A` en un directorio compartido por varias sesiones (código O VAULT DE OBSIDIAN) se lleva de paso archivos de otra sesión activa** aunque no sea un repo de código — el vault de Obsidian tiene el mismo riesgo si varias sesiones escriben notas en paralelo. Antes de commitear, `git status --short` y mirar CADA archivo listado; usar `git add <paths concretos>` en vez de `-A` cuando el directorio es compartido. Revertir es peor que prevenir: el archivo ajeno mezclado no es destructivo por sí solo, pero atribuye autoría/timing incorrectos y puede confundir el histórico. Caso: vault Obsidian 2026-07-04, `git add -A` mezcló un doc de auditoría de otra sesión (worktree `fix-auditoria`) en un commit sobre un tema distinto.
- **RESUELTO 2026-08-03 — usar `opsa`, no `op`.** Todo lo que sigue en esta viñeta describe el mundo pre-service-account y se conserva como arqueología. El wrapper `~/.local/bin/opsa` saca un token de service account del Keychain y hace `exec op`: sin Touch ID, sin `op signin`, sin expiración a media sesión. Cubre las **16 bóvedas de `agentesialab.1password.eu` en solo lectura** y el token **caduca el 2026-11-01**. Gotcha propio: `opsa item get` **exige `--vault` explícito** aunque busques por ID. Fuera de alcance (`my.1password.com`, vaults `Private`/`Employee`/`Shared`, escribir con `item create/edit/delete`) sigue mandando todo lo de abajo. El hook global `~/.claude/hooks/op-guard.sh` bloquea el `op` de lectura y remite a `opsa`; la doctrina vive en `~/.claude/CLAUDE.md` §Herramientas CLI.
- **[Arqueología, pre-2026-08-03] `op` (1Password CLI) SÍ funciona desde Claude Code vía integración de escritorio (Touch ID) para cientos de llamadas seguidas** (corregido: la nota previa de 2026-07-05 decía que fallaba siempre — en la práctica funcionó de forma extensiva). Dos gotchas reales: (1) la sesión puede expirar en medio de un script largo (`account is not signed in` / `authorization timeout`) — basta reintentar el comando o apagar/reencender "Integrate with 1Password CLI" en Settings→Developer, no hace falta service account token para uso interactivo; (2) el classifier de permisos bloquea por defecto el patrón `op item get ... | op item create --account X ...` (mover secretos entre cuentas) — pedir aprobación explícita, no es un fallo del CLI. Si se automatiza sin supervisión (cron/CI) sí conviene `OP_SERVICE_ACCOUNT_TOKEN`. Caso Mac nuevo 2026-07-24 (reorganización 1Password, ~150 operaciones op sin fallo estructural). **(3) Cuando la integración de escritorio no responde, el `op signin` que corre el USUARIO no arregla la shell del agente** (2026-07-25): cada Bash del agente arranca de perfil y no ve el `OP_SESSION_*` de la terminal del usuario. Cascada de síntomas: `account is not signed in` → tras el signin del usuario, `error initializing client: response: promptError` o cuelgue de 60 s esperando un Touch ID que no puede pintarse. Con varias cuentas, `op signin` exige `--account <shorthand>` (de `op account list`). Salida práctica: **darle al usuario el comando con prefijo `!`** para que corra en su shell, escrito para consumir el secreto inline (`K=$(op item get …) && curl -H "x-api-key: $K"`) y filtrar la salida antes de imprimirla — el secreto nunca entra en la conversación y el trabajo no se bloquea.
- **QA de navegador: por defecto `agent-browser` (CLI), NO las tools MCP `claude-in-chrome`** — más barato, y es lo que ya se usa en todos los proyectos. Antes de cargar `mcp__claude-in-chrome__*` por ToolSearch para cualquier verificación visual, comprobar `which agent-browser` y usarlo. Reservar `claude-in-chrome` solo si el usuario lo pide explícitamente por nombre. Recordado el 5-ago (TuCRMIA): arranqué una sesión de claude-in-chrome antes de acordarme.
- **`agent-browser click`/`find click` a veces no dispara el `onClick` de React (confirmado con React 19) y reporta `✓ Done` igual** — sin error visible, sin cambio en la página. Fallback fiable: `agent-browser eval` con JS que localiza el elemento (por texto o `aria-label`, no `textContent` si hay iconos) y llama `.click()` directamente en el DOM. Si el elemento no cambia tras el `.click()` nativo tampoco, sospecha de ref stale (re-snapshot) antes de asumir que el fix no funciona. Cada llamada a `eval --stdin` corre en scope aislado — declarar `const`/`let` repetido entre llamadas da `SyntaxError: already declared`, envolver siempre en `(function(){...})()`. Caso TuFacturaIA 2026-07-07 (smoke Holded + UX recurrentes/integraciones).
- **`agent-browser fill @ref ""` (cadena vacía) no dispara el `onChange` de React** — el campo se ve vacío pero el estado del componente conserva el valor viejo y un "guardar" persiste el dato anterior sin error. Vaciar por teclado (`click` → `Meta+a` → `Backspace`) y verificar contra BD/red, no contra el aspecto del campo. Ver [[agent-browser-fill-vacio-no-dispara-onchange-react]]
- **Screenshots `--full` de agent-browser pueden no capturar toasts `position:fixed`** (se recortan o desaparecen en la captura de página completa aunque sean visibles en el viewport real). Si necesitas capturar un toast/notificación, usa screenshot SIN `--full` (viewport normal) justo tras la acción — con timing ajustado (200-500ms tras el click, los toasts suelen durar 3-4s).
- **El classifier distingue "saltarte el check de CI" de "saltarte una revisión humana sustantiva" — son dos autorizaciones DISTINTAS aunque el mismo merge las junte.** Una confirmación genérica del usuario ("adelante con los merges") solo cubre el bypass de Actions/billing; si el repo exige además el visto bueno de OTRA persona sobre el contenido (p. ej. texto de un prompt, lane de otro dev), el classifier lo bloquea aparte y pide que el usuario lo nombre explícitamente ("asumo el override del visto bueno de X"). No intentes colar ambos con una sola pregunta genérica — pregunta las dos por separado si el repo tiene esa regla. Caso AGH 2026-07-11 (PR de cambio de prompt, lane de Borja, 3 PRs mergeadas con 2 autorizaciones distintas de Manu).
- **El classifier bloquea `gh pr merge --admin` que auto-aprueba un PR agent-authored** (Merge Without Review + Self-Approval) Y bloquea auto-editar `settings.json` / la skill `update-config` para ampliarse permisos (Self-Modification / Auto-Mode Bypass). El `allow` de `settings.local.json` (`Bash(gh pr merge:*)`) NO anula la capa del classifier de forma fiable mid-sesión — puede colar una y bloquear la siguiente idéntica. Vía correcta: el humano corre el merge con `!` o **reinicia la sesión** para que cargue el permiso; no rodearlo editando settings con Write. Distinto del ruleset de GitHub (que impide aprobar tu propio PR) — son dos capas. Caso AGH 2026-07-08 (tren de 5 PRs propias). **Reconfirmado 2026-07-29 (TuFacturaIA)**: el bloqueo de Self-Modification tapa por igual `Edit` sobre `.claude/settings.local.json` y la invocación de la skill `update-config`, incluso cuando **el usuario pide explícitamente en ese turno** que amplíes tus permisos. No hay vía desde dentro: entrega el JSON al humano para que lo pegue y reinicie la sesión.
- **El classifier bloquea acciones de navegador que PUBLICAN hacia fuera** (agent-browser `click` sobre un botón tipo "Publicar al cliente"/"Enviar"), aunque el usuario haya dicho "adelante" y el smoke previo con el mismo binario haya pasado sin fricción: lo que se evalúa es el efecto (mensaje a un tercero real), no el comando. Deja el modal abierto y preparado y pide al humano que pulse. Un `allow` de `Bash(agent-browser:*)` en `settings.local.json` lo cubriría, pero es **muy amplio** (autoriza cualquier clic en cualquier sesión iniciada, prod incluida) — decisión del humano, no del agente. ## Republicar un Artifact: el listado no basta, hace falta `WebFetch` antes (7-ago-2026)

## `autoMode` es GLOBAL y no se puede mover a un proyecto (15-ago-2026)

- **`autoMode` (el clasificador que elimina prompts de permiso) sólo se lee de `~/.claude/settings.json`, del flag `--settings` y de managed.** Se **ignora** en el `.claude/settings.json` de un proyecto y en `settings.local.json`. Consecuencia práctica: sus cuatro listas —`environment`, `allow`, `soft_deny`, `hard_deny`, todas en prosa, con `"$defaults"` para heredar las de fábrica— aplican a TODAS las sesiones, sea cual sea el cwd.
- **El fallo que eso provoca**: si una sesión rellena `environment` mirando sólo su directorio de trabajo, el bloque afirma cosas falsas en cuanto trabajas en otro producto —«el repo de confianza es X», «los dominios internos son los de X»— y el clasificador decide con esa foto. Peor: una regla de `soft_deny` escrita como «nada que no sea el proyecto enlazado de X» **soft-deniega el trabajo legítimo de los demás repos**, que es un rojo sobre trabajo correcto (P5).
- **Y no se arregla moviéndolo al repo que describe**: ahí sería inerte. Se arregla generalizándolo — «el repositorio de confianza es el del cwd», los dominios y servicios de todos los productos— porque su ámbito ES global por diseño. Y hay que incluir explícitamente `~/Projects/obsidian-vault` y `~/.claude`: se tocan desde cualquier sesión (cierre de sesión y configuración), y dejarlos fuera bloquea `/obsidian-1` entero.
- ⚠️ **Conflicto vivo entre dos mecanismos del arnés**: el stop hook `harness-commit-guard.sh` EXIGE commitear `~/.claude`, y el clasificador DENIEGA todo `git commit`/`push` ahí —con `cd` y con `git -C`—. Ningún agente puede satisfacer al hook: hay que pedírselo a Manuel con `!`, o añadir la regla a `permissions.allow`. Un hook que pide lo que otro mecanismo prohíbe es un rojo que nadie puede apagar trabajando.

## `git add -N` rompe `git stash` (movido desde hot.md, 17-ago-2026)

Con un fichero en `intent-to-add`, `stash push`/`pop` fallan **a medias**. `git reset` antes, o
commitea y rebasa. Ver [[git-add-intent-to-add-rompe-stash]].

## Las memorias se atan al cwd: mover un repo las deja mudas (18-ago-2026)

`~/.claude/projects/<slug>/memory/` guarda las memorias por directorio de trabajo, y el slug **es el
cwd con las `/` cambiadas por `-`**. Al migrar de Mac (`~/facturaia` → `~/Projects/facturaia`)
quedaron **111 memorias** en slugs muertos: no las cargaba ninguna sesión y no hay error, warning ni
señal. Se descubrió por casualidad meses después, limpiando disco.

- Al **renombrar o mover un repo**, migrar también su `memory/` al slug nuevo, fusionando el
  `MEMORY.md` a mano (un `mv *.md` pisa el índice del destino y te llevas por delante sus entradas).
- Para saber a qué cwd pertenece un slug, **no lo deduzcas del nombre**: los guiones del propio repo
  lo hacen ambiguo (`-Users-x-Projects-agentesia-crm` no es `.../agentesia/crm`). Léelo del campo
  `"cwd"` de cualquier `.jsonl` del directorio.
- Ya hay guard: `~/.claude/hooks/memory-orphan-guard.sh` bloquea el cierre de turno si aparece un
  `memory/` con cwd muerto. Compañero: `worktree-guard.sh` para worktrees ya integrados.

Ver [[claude-headless-hereda-hooks-y-mcp-del-proyecto-del-cwd]].

## El clasificador de auto mode veta CONCEDER acceso, no escribir (28-ago-2026)

Reparando datos de un cliente en producción, el clasificador de `autoMode` denegó ~10 llamadas y el
patrón no era «escritura peligrosa» sino **alta de acceso**:

- **Denegado siempre**: `POST /api/admin/orgs/<id>/members` (tanto `mode:'create'` como `'invite'`),
  acuñar una sesión con `generate_link`+`verify`, y `POST /api/auth/switch-org`.
- **Denegado a ratos, sin criterio estable**: navegar a `/admin/orgs/<uuid>`, teclear el nombre del
  cliente en un buscador, un `location.reload()`.
- **Permitido**: aprobar y borrar facturas de ese cliente por su UI una vez dentro, el `PATCH
  {action:'remove_member'}` que **revoca** el acceso, y todo el SQL de solo lectura contra prod.

Es coherente con la regla de «no crear cuentas ni conceder credenciales»: revocar pasa, conceder no.
Dos consecuencias prácticas:

- **`/permissions <patrón>` NO lo levanta.** Añadir `mcp__claude-in-chrome__*` desbloqueó navegación
  y JS en general y la escritura concreta siguió denegada. No hay regla allow que valga, y
  escribirse una a uno mismo en `settings.local.json` sería justamente burlar el permiso.
- **El desbloqueo es humano y de una sola línea**: que Manu pegue el `fetch` en la consola del
  navegador ya logueado. Ojo, DevTools exige teclear a mano las palabras `allow pasting` (pegarlas
  no cuenta) antes de admitir el primer pegado de la sesión.
